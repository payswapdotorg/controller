# Pectoraux Controller

The Controller is the orchestration runtime for governed software delivery across Pectoraux repositories.

It does **not** replace WorkflowOS, does not own product architecture, and does not become a second source of truth. The repository contains the controller's frozen architecture, implementation roadmap, machine state, work orders, and worker/reviewer contracts.

## Mission

Automate the mechanical loop:

`READY work item → dispatch Z.ai → implementation PR → CI → Architect review → change loop → approval → merge → post-merge reconciliation → next eligible work item`

The controlled repository remains authoritative for roadmap, work-item scope, acceptance criteria, and program state. GitHub is the execution/event surface. Z.ai is the implementation worker. The Architect is the semantic review gate.

## First implementation rule

The Controller itself is built using the same governed work-item process it will eventually automate. No implementation work should bypass the repository roadmap or work-order contract.

## Bootstrap rule

The Controller does not exist yet, so the human operator initially performs its mechanical orchestration role. Automation is introduced incrementally; the Architect must explicitly announce each automation stage and tell the operator which manual duties have been removed. See `spec/operations/controller-build-process.md` for the exact bootstrap loop and stage-by-stage responsibility transition.

## Development

The controller package is pure Python standard library (Python >= 3.10, no runtime dependencies, no network access, no credentials). All commands run from the repository root.

Run the test suite:

```sh
python -m unittest discover -s tests -t .
```

Validate repository authority and reconstruct controller state (offline smoke test):

```sh
python -m controller validate --repo .
```

Reconstruct and inspect the governed work-item domain model (identity, lifecycle position, authority-derived dispatch eligibility):

```sh
python -m controller domain --repo .
```

Report the offline routing view — authority, lifecycle position, and the owning boundary for the next step (no network, no provider tokens):

```sh
python -m controller status --repo .
```

### Domain model (CTRL-002)

`controller/domain.py` defines the typed domain model for the single active governed work item: `WorkItemIdentity` (repository-resolved identity), `AuthorityContext` (governing documents and automation stage), `DispatchEligibility` (authority-derived dispatch verdict with an auditable basis), `GovernedWorkItem` (the immutable aggregate), and `DomainCommand`/`DomainEvent` (the domain-level command/event contracts with deterministic `serialize()`/`deserialize()` for future GitHub and Z.ai adapters — no transport is implemented). The domain layer delegates all lifecycle semantics to the CTRL-001 frozen transition table and never redefines transition policy. Dispatch eligibility requires the active work item to be READY with machine state and its work order in agreement, and not already recorded in `completed`; anything else fails closed with typed errors. The model is a pure projection of repository authority: no database, cache, or runtime state.

### GitHub adapter (CTRL-003)

`controller/github.py` is the typed GitHub adapter boundary. `GithubAdapter` takes an injected `GithubTransport` (Protocol); `UrllibGithubTransport` is the only network component in the package and receives its token strictly as a constructor argument (never from repository files or defaults, never logged). Observations (branches, commits, PRs, reviews, comments, commit statuses) normalize into frozen typed values deterministically — lists sorted by stable IDs, timestamps preserved as ISO strings, reviews carry the exact reviewed commit (`commit_id`), malformed responses fail closed as `GithubMalformedResponseError`. Work-order correlation (`correlate_work_pull_request`) enforces the one-PR-per-work-item rule and exact base/head SHA identity (`GithubNotFoundError` / `GithubAmbiguityError` / `GithubStaleBaseError`). Mutations are policy-gated: `create_branch` requires an explicit authority-derived base SHA; `open_pull_request` refuses one-PR violations and base drift; `merge_pull_request` executes only after it **independently re-establishes the complete merge-policy proof** (FZ-CTRL003-004A, the Architect-accepted execution-time re-proof path). `authorize_merge` evaluates the frozen merge predicate — the intended base *ref and SHA*, exact head, clean mergeability, one-PR, terminal-success required checks, an Architect APPROVE **bound to the exact reviewed head SHA** (`commit_id` must match; an approval of an older commit does not survive a head change) with no later CHANGES_REQUESTED, and the CTRL-002 authority-derived `DispatchEligibility` identifying exactly the work item as the active eligible item — and returns a `MergeAuthorization`, which is a merge *request* (target identity), never evidence: `merge_pull_request(authorization, eligibility=…, architect_reviewer=…, required_checks=…)` re-evaluates that same predicate *in full* from live GitHub state plus fresh execution-time inputs immediately before the remote mutation, and requires the presented authorization to be field-identical to what the gate would issue right now (policy parameters are deliberately not carried in the authorization, so nothing in the presented object can weaken the re-proof). Possession of a fabricated, altered, or incomplete authorization therefore cannot bypass policy (`GithubAuthorizationForgedError` for structurally invalid or non-identical requests; the predicate's typed refusals otherwise — always with zero remote mutations): a caller with access to every public and module symbol can construct the value, but the merge only executes when the re-proven predicate — including the Architect APPROVE on the exact head — actually holds. The predicate lives in a single private method shared by both paths, so gate and execution can never drift apart. Authorizations are in-process values and are never serialized or reconstructed from external data. The adapter treats GitHub as evidence, never authority; all authority facts are caller inputs. The test suite exercises the adapter exclusively through deterministic fakes (`tests/github_fakes.py`) — no network or credentials are needed.

### Z.ai worker adapter (CTRL-004)

`controller/zai.py` is the typed Z.ai implementation-worker adapter boundary. `ZaiAdapter` takes an injected `ZaiTransport` (Protocol); `UrllibZaiTransport` is the only Z.ai-provider network component in the package and receives its API root and token strictly as constructor arguments (never from repository files or defaults, never logged). The adapter exposes exactly two operations — `start_worker(context)` and `resume_worker(context, session_id)` — and deliberately has **no merge, approval, completion, or architecture-mutation capability** (worker safety boundary, AC6). Every request is bound to the caller-supplied `ZaiWorkerContext`: the exact repository identity, Work Order path (and optional content), active work-item identity, base SHA (40-hex), and PR/head identity for a change iteration — validated in full *before any provider I/O*; a missing, contradictory, or stale identity fails closed (`ZaiContextMismatchError`). A fresh start carries no review packet; a resume propagates the caller's review findings **verbatim** in the instruction payload and must match the named session's reported work item, repository, base, and PR identity exactly — a mismatched session (a silent fork) or a different reported session id refuses the operation (`ZaiContextMismatchError` / `ZaiContradictionError`). Worker instructions are *constructed* by the adapter from typed repository-derived facts plus the frozen worker-role contract (may/may-not lists from the architecture's Z.ai boundary); there is no free-text instruction channel, so only controller-approved instructions can ever be sent, and a defense-in-depth payload policy fails closed on unknown fields or token-like material (`ZaiPolicyViolationError`). Provider responses normalize deterministically into frozen **adapter-issued evidence** — `ZaiIssuedWorkerSession` values (session id, bound work identity, PR context, status and ISO timestamp preserved verbatim) sealed inside the adapter's provider-response path itself with the proof binding exactly the ordinary fields (FZ-CTRL007-001/002/003/004); malformed responses fail closed (`ZaiMalformedResponseError`). This is genuine construction-path evidence with **no source-level secret and no reachable mint operation** (FZ-CTRL007-004): the capability is a fresh runtime object captured in the closure that installs the adapter's operations (`_install_provider_response_path` — not repository source material, not a module attribute, not importable, never stored on issued values), and **no module-level callable accepts provider-report data** — the normalization/issuance closure exists solely inside `start_worker`/`resume_worker`, so the only issuance path demands an actual provider response flowing through those operations, and a genuine proof transplanted onto different fields fails because the seal binds the exact fields. `is_adapter_issued()` is a pure local check (zero provider I/O) distinguishing adapter-issued evidence from a structurally identical hand-constructed `ZaiWorkerSession`, a caller-constructed value of the issued type, or a transplanted proof — and never a subclass of the issued type: the check pins the exact dynamic type before invoking the sealed verifier, and governing boundaries (the CTRL-007 review loop) invoke the sealed adapter verifier directly against the carried proof and ordinary fields instead of dispatching on the virtual method (FZ-CTRL007-005) — verification is available to consumers; minting is not; the issued type is the same frozen value type (not a second session model, not a registry/cache/persistence — the closure creates nothing per issuance and accumulates no state), and issued evidence is in-process by construction: nothing persists sessions, and a restart re-issues through the adapter. The session identifier is an explicit, non-authoritative execution reference the controller may carry — the adapter keeps no registry, cache, or persistence, never reads repository files, and never treats provider state as authoritative over repository machine state (`ZaiAdapterError` family: configuration, auth, rate limit, transport, rejected request, malformed, missing session, context mismatch, contradiction, policy violation). The test suite exercises the adapter exclusively through deterministic fakes (`tests/zai_fakes.py`) — no network or credentials are needed.

### Orchestrator (CTRL-005)

`controller/orchestrator.py` is the deterministic orchestration boundary coordinating the accepted domain model, GitHub adapter, and Z.ai adapter for exactly one active governed Work Order. `Orchestrator(github=…, zai=…)` holds only the two injected adapters — no database, local session store, cache, or runtime state — so a restart reconstructs the same governed decision from the same repository authority, remote evidence, and caller-carried references: `run_cycle(repo_root, references)` is a pure deterministic function of its inputs (restart reconstruction, AC6). Every cycle begins from a full authority reconstruction (`reconstruct_domain`): missing, malformed, stale, or contradictory machine state, roadmap, or work-order authority fails closed with typed errors *before any remote action* (AC1). The cycle then performs exactly one governed step — one transition already authorized by the frozen table, derived from observed evidence, or one pure observation that issues no command (AC4); repeated observation of non-terminal evidence is idempotent. Correlation (AC2): the governed facts that live outside repository authority are supplied by the caller as `OrchestrationReferences` (governed branch, dispatch base SHA, the **typed `ZaiWorkerSession` request** naming the worker execution, architect reviewer identity) — non-authoritative carried inputs, cross-validated against authority and remote evidence, never guessed and never stored; a missing reference fails closed (`OrchestrationMissingReferenceError`), and a carried session whose binding (repository, active Work Item, dispatch base SHA) contradicts reconstructed authority fails closed with `OrchestrationContradictionError` *before any lifecycle event or remote call* — a bare session-id string is not an accepted carried form. The `DISPATCHED → IMPLEMENTING` transition additionally re-establishes **provenance** from live provider state (FZ-CTRL005-002): `start_worker` with the exact repository-derived context *identifies* the worker execution for that exact Work Order (an existing accepted CTRL-004 contract), and the provider-identified session must be the very session the caller carried — the fork guard mirrors the adapter's own resume fork refusal — so a session value constructed by hand, however structurally exact, cannot advance the lifecycle without the provider identifying it right now; no PR identity is invented while still DISPATCHED. GitHub PR correlation enforces the exact work-item/PR identity through the CTRL-003 adapter (branch + base SHA, one-PR rule); the Z.ai start context is constructed exclusively from repository authority (work order path/content, exact base SHA observed from the base branch) and the resume context preserves the same governed worker/PR identity across a change iteration, re-observing the review packet from GitHub on every cycle and propagating it verbatim (AC3). Contradictions fail closed (AC5): repository authority outranks remote observation — a lifecycle position that records a PR-open-or-later position with no governed PR observed, or a CHANGES_REQUESTED position whose latest architect-review evidence no longer matches, stops the run with `OrchestrationContradictionError`; there is no guessed recovery and no alternate-item dispatch. The downstream boundary (AC7) is explicit: merge, reconciliation, and advancement positions return a typed `DownstreamHandoff` naming the owning future stage (CTRL-006+); the orchestrator never merges, approves, reconciles, or advances, and its only remote mutations are `start_worker` / `resume_worker` — and only after the governed command validates. The test suite exercises the orchestrator exclusively through the deterministic GitHub/Z.ai fakes (`tests/test_orchestrator.py`) — no network or credentials are needed.

### CI/evidence gate (CTRL-006)

`controller/evidence.py` is the deterministic CI/evidence gate. `EvidenceGate(github=…)` holds only the injected GitHub adapter — no database, cache, registry, scheduler, or queue — and never talks to the worker provider: `evaluate(repo_root, references, policy)` is a pure deterministic function of repository authority, observed GitHub evidence, caller-carried references, and the supplied frozen policy, so a restart replays the same decision (AC7). Every evaluation begins from a full authority reconstruction through the CTRL-002 domain layer; a lifecycle position outside the gate's CI evidence positions (PR_OPEN, CI_PENDING) fails closed with `EvidenceGatePositionError` before any remote observation (AC1). Correlation (AC2) reuses the CTRL-003 adapter's `correlate_work_pull_request` with the same `OrchestrationReferences` vocabulary the orchestrator consumes (governed branch, dispatch base, typed worker session — no parallel reference model): foreign, stale, or ambiguous correlation propagates the adapter's typed errors, and an absent governed PR at a CI position is an `EvidenceContradictionError`, never a guess. Classification (AC3/AC4) applies the frozen rules documented on the module — per required check: `success` is terminal-success, `failure`/`error` terminal failure, `pending` pending, any other value or a duplicated context policy-blocked, and a missing required check pending only while the combined status is still `pending` — with aggregate precedence POLICY_BLOCKED > TERMINAL_FAILURE > PENDING > TERMINAL_SUCCESS, and unrelated observed contexts reported without affecting the verdict (the required set defines the gate; the frozen merge predicate stays authoritative at merge time). The policy itself is a fresh caller-supplied `EvidencePolicy(required_checks, retryable_checks)` input, structurally validated and canonicalized, mirroring `required_checks` in the CTRL-003 merge predicate: the gate executes policy, it never invents repository facts. The outcome is one frozen `EvidenceGateOutcome` carrying the classification, the per-check detail (successful/pending/failed/missing/blocked/unrelated, all sorted), the exact correlated PR identity, and the raw observed status for downstream review/merge decisions. The one governed lifecycle step (AC6) is requested through the CTRL-002 domain model so the frozen CTRL-001 transition table remains the single validity authority: AWAIT_CI from PR_OPEN (mirroring the orchestrator), RECORD_CI_SUCCESS from CI_PENDING only on terminal-success evidence; every other classification observes without an event, and at most one transition is ever applied per evaluation. The retry boundary (AC5) is a typed `EvidenceRetryRequest` — a *request*, never an execution: it is emitted only when every failing required check is declared retryable by the policy and the carried typed worker session proves its binding (repository, active work item, dispatch base — the FZ-CTRL005-001 doctrine facts — plus PR identity when the session reports one, refusing stale or forked evidence with `EvidenceContradictionError`); the consuming boundary re-establishes session provenance from live provider state through the CTRL-004 adapter before any resume, mirroring the merge-authorization request/re-proof doctrine. An absent session reference leaves the failure exposed for governance attention without guessed recovery; the gate performs zero remote mutations at all times. The test suite exercises the gate exclusively through the deterministic GitHub fakes (`tests/test_evidence.py`) — no network or credentials are needed.

### Architect review loop (CTRL-007)

`controller/review.py` is the governed Architect-review loop. `ArchitectReviewLoop(github=…)` holds only the injected GitHub adapter — no Z.ai surface of any kind, no packet registry, decision cache, scheduler, or queue — performs zero worker-provider calls, never authors a decision, and never resumes a worker: `evaluate(repo_root, references)` is a pure deterministic function of repository authority, observed review/comment evidence, and caller-carried references, so a restart replays the same decision (AC7). Every evaluation begins from a full authority reconstruction through the CTRL-002 domain layer; a lifecycle position outside the loop's decision positions (REVIEW_PENDING, CHANGES_REQUESTED) fails closed with `ReviewLoopPositionError` before any remote observation (AC1), and correlation reuses the CTRL-003 adapter plus the CTRL-005 `OrchestrationReferences` vocabulary (governed branch, dispatch base, typed worker session, architect reviewer identity — no parallel reference model): foreign, stale, or ambiguous PR correlation propagates the adapter's typed errors, and an absent governed PR is a `ReviewContradictionError`, never a guess (AC2). The decision channel is the accepted review evidence: only reviews authored by the carried architect reviewer identity are authoritative, the latest is selected by the deterministic `(submitted_at, review_id)` order, and only the observed GitHub review states `APPROVED` and `CHANGES_REQUESTED` map to the protocol decisions APPROVE and REQUEST_CHANGES — every other state (COMMENTED, PENDING, DISMISSED) is a non-decision the loop refuses to infer from, a decision whose `commit_id` does not bind to the exact PR head is stale and never the current decision, and APPROVE is never a merge command: the loop performs zero remote mutations on the GitHub side (AC3). For REQUEST_CHANGES the Architect's durable machine-readable packet — a fenced ` ```review-packet ` block in an architect comment on the governed PR, in the frozen grammar instantiated from `spec/governance/review-protocol.md` (exact keys, order, indentation, and vocabularies) — is parsed strictly in the raw block exactly as it stands (FZ-CTRL007-006: blank or whitespace-only lines are never silently discarded — any such line fails closed; structural lines match their exact forms, `findings:` / `findings: []` as whole exact lines, `pr` and `iteration` as canonical decimal digit strings — `int()` laxity never normalizes a packet — `work_item` as the exact identity token without surrounding whitespace, SHAs as exactly 40 lowercase hex characters, so trailing whitespace or garbage is rejected instead of being absorbed into a value; findings' declared text remains transported verbatim), cross-validated field-by-field against the observed evidence (work item from authority, correlated PR, exact head, base, the deterministic iteration count, the observed decision), and transported verbatim as a typed `ReviewPacket` with `ReviewFinding` values carrying the stable finding IDs, severity, affected paths, criterion, and required changes; foreign packets (another work item or PR) are contradictions, stale packets (older head/iteration) are history and never reinterpreted, zero or multiple matching packets fail closed with `ReviewPacketError`, and findings are never dropped, rewritten, or invented (AC4). The typed `ReviewHandoff` (AC5) — produced only after the carried session's **ordinary binding** is proven locally (repository, work item, dispatch base, PR identity when reported — the FZ-CTRL005-001 doctrine facts, with foreign/drifted sessions failing closed with zero remote calls) and its **adapter-issued provenance** is verified locally (FZ-CTRL007-001/002/005): the carried value must be exactly `ZaiIssuedWorkerSession` — evidence sealed at the CTRL-004 boundary inside the adapter's provider-response operations — and its construction-path proof must verify, a pure local computation with no source-level secret, no reachable mint (no module-level normalization callable exists), and zero worker-provider I/O of any kind (the loop holds no Z.ai adapter instance and makes no provider call; the one sealed-verifier reference is a pure static zero-I/O check; observation-only contract). The provenance check is non-overridable (FZ-CTRL007-005): the loop never dispatches on the value's virtual `is_adapter_issued()` method — a subclass could override it — but pins the exact dynamic type to the sealed evidence class and invokes the sealed adapter verifier (`ZaiAdapter._verify_issuance`) directly against the carried proof and the canonical ordinary fields, so a subclass of the issued type is rejected before verification, whether it overrides the virtual method to claim issuance or carries a genuine stolen proof: adapter provenance is construction-path evidence, never behavior supplied by the carried object's dynamic type. A structurally exact hand-constructed `ZaiWorkerSession` value, a caller-constructed value of the issued type, a subclass of the issued type, or a genuine proof transplanted onto different fields cannot produce a handoff; live provider re-proof/resume belongs to the consuming worker boundary. The handoff — the proven session id, the exactly correlated PR identity, and the validated packet — is a *request* for the existing worker/resume boundary, never an execution: the loop never calls `resume_worker` (the boundary performs the resume itself); an absent session reference leaves the packet exposed without a handoff, and the loop never dispatches an alternate worker or creates a new PR. Deterministic iteration control (AC6): at most one governed transition per evaluation — APPROVE or REQUEST_CHANGES from REVIEW_PENDING, both already authorized by the frozen CTRL-001 table via the CTRL-002 domain model — pure observation otherwise; at CHANGES_REQUESTED the loop re-observes and rebuilds the identical packet and handoff without an event (idempotent, restart-safe), a vanished or flipped decision at that position is a contradiction, and the iteration number is the deterministic count of the architect's CHANGES_REQUESTED reviews on the governed PR — a new iteration requires a new current head and a new authoritative packet. The test suite exercises the loop exclusively through the deterministic GitHub/Z.ai fakes (`tests/test_review.py`) — no network or credentials are needed.

### Merge + reconciliation boundary (CTRL-008)

`controller/merge.py` is the governed merge + post-merge reconciliation boundary. `MergeReconciliationLoop(github=…)` holds only the injected GitHub adapter — no Z.ai surface of any kind (the module imports nothing from `controller.zai`), no state, cache, database, scheduler, or queue — so a restart replays the same decision from the same repository authority, evidence, carried references, and policy (AC7). Every evaluation begins from a full authority reconstruction through the CTRL-002 domain layer; a lifecycle position outside the merge boundary (APPROVED, MERGING, MERGED, RECONCILING) fails closed with `MergeLoopPositionError` before any remote observation (AC1), and correlation selects the unique PR for the carried governed branch across its **whole history** (state `all`, not open-only — the boundary observes the PR before and after the mutation) on the intended `main` base ref, with the merge-boundary base **identity** taken from the correlated PR's *observed current* base SHA — the exact current `main` base the PR represents (GitHub reports the base-branch head for an open PR and freezes the merge-time base for a merged one): the carried dispatch-base SHA is recorded as distinct *provenance* on every outcome (`dispatch_base`, never a predicate input), because an explicitly absorbed post-dispatch `main` advancement is legitimate (FZ-CTRL008-001 — the real PR #23 shape: dispatch base `f55f519`, current base `c67bc66`), while a base that drifts between authorization and execution still refuses the mutation at the execution-time re-proof and zero, multiple, or foreign-base correlation is a `MergeContradictionError`, never a guess (AC2). The merge mutation is executed **only** through the CTRL-003 adapter: `MergePolicy.required_checks` (the same required-CI vocabulary CTRL-006 consumes, canonicalized and validated — the loop duplicates no classification logic) feeds `authorize_merge`, which evaluates the complete frozen predicate from live GitHub state — intended `main` base ref and SHA, exact head, clean mergeability, the one-PR rule, terminal-success required CI, an Architect `APPROVE` bound to the exact current head with no later `CHANGES_REQUESTED`, and the authority-derived active-item binding — and `APPROVE` alone never merges (AC3). The loop binds repository authority through a **derived** merge-boundary eligibility (the FZ-CTRL003-001 doctrine at this boundary): the value is computed — never hand-authored — from the same reconstruction that produced the governed item (the active-item identity authority records, the completed ledger, the proven merge-boundary position), answering the predicate's frozen question “is this the active, not-yet-completed item seeking merge authorization”; a completed item can never again seek a merge. `merge_pull_request` then re-establishes the complete proof immediately before the single `PUT` (execution-time drift protection, AC4) — the loop performs **at most one merge attempt per evaluation for one exact authorized head**, with no intra-loop retry of any kind: a refused, failed, or drifted merge surfaces typed for governance attention, and a later evaluation is a fresh governed cycle. Only the observed GitHub merge result establishes `MERGED` (AC5): the merged flag, closed state, intended base ref, and reported merge commit SHA (now carried on `GithubPullRequest.merge_commit_sha` — observed evidence extracted verbatim from the same raw PR observation, the extension the frozen predicate's vocabulary required for recording the exact merge SHA; normalization determinism is preserved and the frozen predicate itself is untouched). A merge that already landed — an earlier cycle whose state write did not survive, or an externally performed authorized merge — is recorded, never re-attempted; a missing, contradictory, or unmerged observation at a post-execution position fails closed with no second attempt. One governed transition per evaluation (`MERGE` from APPROVED, `RECORD_MERGE` from MERGING, `RECONCILE` from MERGED, `RECORD_RECONCILIATION` from RECONCILING), each already authorized by the frozen CTRL-001 table through the CTRL-002 domain model. At RECONCILING the loop derives the deterministic `ReconciliationRecord` (AC6) from authority plus merge evidence — the completed ledger extended by exactly the active item (a duplicate completion is a contradiction, not a no-op), the exact merge SHA, the deterministically selected next eligible work item (the unique not-completed work order declaring `READY`; none means the successor is not yet defined/activated, more than one is a one-active-item contradiction), and the automation stage preserved verbatim — as a typed value the runtime persists through the governed commit; the loop itself mutates no authority file, and the record is always re-derived (never deserialized), so repeated evaluation is idempotent by construction. The worker-merge prohibition is enforced by the predicate itself: an Architect `APPROVE` authored by the carried architect reviewer identity and bound to the exact head is evidence a worker cannot produce for its own PR. The test suite exercises the boundary exclusively through deterministic stateful GitHub fakes (`tests/test_merge.py`) — no network or credentials are needed.

### Recovery boundary (CTRL-009)

`controller/recovery.py` is the governed recovery boundary: deterministic restart/interruption classification for exactly one active governed work item. `RecoveryBoundary(github=…)` holds only the injected GitHub adapter — no Z.ai adapter instance, no worker-provider call of any kind (the only Z.ai references are the session types and the sealed static verifier, the FZ-CTRL007-005 doctrine), no database, cache, queue, scheduler, or registry — so a restart replays the same classification from the same inputs (AC6). Every evaluation begins from a full authority reconstruction through the CTRL-002 domain layer: missing, malformed, stale, or contradictory authority fails closed with the CTRL-001/002 typed errors before any remote observation, and a terminal exception state (BLOCKED/ESCALATED/CANCELLED) has no recovery by definition (`RecoveryTerminalStateError`) (AC1). The boundary then requires the carried branch and dispatch-base provenance references (the CTRL-005 `OrchestrationReferences` vocabulary — no parallel reference model), correlates the governed PR across its **whole history** (the CTRL-008 correlation vocabulary: unique PR for the branch, intended `main` base ref; zero/multiple/foreign-base fail closed with `RecoveryContradictionError`), and — when a worker session is carried — proves its identity locally with zero provider calls: the FZ-CTRL005-001 ordinary-binding facts (repository, Work Item, dispatch base, PR identity when reported — stale identity is history, not permission) plus adapter-issued provenance through the sealed CTRL-004 verifier with the exact dynamic type pinned (a subclass, a transplanted proof, or a plain hand-built value of the issued type never verifies; the ordinary request form is carried as REQUEST_FORM, its live provenance re-proof belonging to the consuming worker boundary, FZ-CTRL005-002) (AC3). The position-appropriate correlation doctrine then applies: **pre-merge positions** (READY through CHANGES_REQUESTED) enforce the frozen CTRL-003 exact-dispatch-base doctrine — a closed PR (the pre-merge correlation is open-only, so a deeply-behind state whose merge already landed is an unsupported condition stopping for governance) or a base-drifted PR is a contradiction, while an open PR at an earlier position is EVIDENCE_AHEAD (the durable record of work already performed, e.g. the PR opening while still IMPLEMENTING); **merge-boundary and completed positions** apply the FZ-CTRL008-001 doctrine — the observed current base is the identity, the dispatch SHA is provenance only. The typed `RecoveryPlan` (AC2) names the **first incomplete governed boundary** and the frozen-table next step: the orchestrator (DISPATCH/BEGIN_IMPLEMENTATION/OPEN_PR/AWAIT_CI/RESUME_IMPLEMENTATION — with one replay-proof exception: at READY/DISPATCHED while a governed PR is already observed the plan directs NO next step, because the PR is durable evidence the dispatch/start work already ran and the orchestrator's READY/DISPATCHED cycles re-perform the provider start — the recovery continuation can never cause a second worker/provider execution for one Work Item, FZ-CTRL009-001), the CTRL-006 evidence gate (RECORD_CI_SUCCESS — the gate remains the CI classification authority; recovery carries the raw observed combined-status state verbatim), the CTRL-007 review loop (an observed current architect decision, selected by the deterministic `(submitted_at, review_id)` order and bound to the exact PR head, is transported verbatim as classification evidence — never parsed into a packet, never authored, never inferred; non-decision states and stale bindings are history, and a vanished or flipped decision at CHANGES_REQUESTED is a contradiction — and the CHANGES_REQUESTED resume is session-required: an absent carried worker session fails closed with `RecoveryMissingReferenceError` — a resume directive without the exact session identity is never emitted, FZ-CTRL009-002), the CTRL-008 merge boundary (an observed successful merge in the exact CTRL-008 evidence form classifies EXTERNAL_COMPLETION_OBSERVED for the external-merge continuation — record, never re-attempt), or Architect-side governance (COMPLETE/NEXT_READY — the worker never advances or claims completion) (AC4). Partial-operation safety (AC5): MERGING with an unmerged PR classifies PARTIAL_MUTATION_UNRESOLVED — stop for governance attention, the mutation is never retried automatically across the governance boundary; state ahead of evidence (a PR-open-or-later position with no PR, MERGED/RECONCILING/COMPLETE without observed merge evidence) fails closed. Recovery performs **zero mutations of any kind**: no lifecycle command is applied (zero `item.handle` call sites), no remote mutation is issued (only the three GET observations — whole-history PR listing, the combined status at CI positions, architect reviews at review positions — each made exactly where the position's classification needs it), and no authority file is touched; the plan is a *direction* for the runtime to invoke the boundary that owns the next step, whose own frozen predicate performs and authorizes the resumed work (AC7), with a deterministic `basis` audit trail (the `DispatchEligibility` precedent). Repeated evaluation against unchanged authority/evidence returns an equal plan — restart-safe and idempotent by construction (AC8; `tests/test_recovery.py` covers every lifecycle position, evidence-present/state-missing cases, stale/foreign/duplicate/ambiguous evidence, the literal production-SHA FZ-CTRL008-001 shape, session identity binding and refusal, restart equivalence, authority immutability, the FZ-CTRL009-001 no-start-replay regressions (READY/DISPATCHED with an observed PR direct no step — no Z.ai invocation can be caused by the recovery continuation — and the boundary surface holds no worker-execution site), the FZ-CTRL009-002 required-session fail-closed, and the zero-mutation/zero-fabrication properties, all offline through the deterministic GitHub/Z.ai fakes).

### End-to-end dogfood (CTRL-010)

`controller/dogfood.py` is the composed governed-loop proof: one deterministic scenario that executes a complete Work Item lifecycle end-to-end — READY dispatch through the final `COMPLETE` reconciliation — using **only the accepted CTRL-001 through CTRL-009 boundaries** (repository authority reconstruction, the CTRL-005 orchestrator for dispatch/implementation/PR/CI-wait/resume steps, the CTRL-006 evidence gate for CI classification, the CTRL-007 review loop for the Architect decisions, the CTRL-008 merge/reconciliation loop for the frozen merge predicate and the deterministic reconciliation record, and the CTRL-009 recovery boundary for the restart classification). The dogfood layer *composes*: it defines the frozen scenario identities (one work item, branch, PR, dispatch base, two successive heads, one worker session, one Architect reviewer, the required CI checks, the observed merge commit), materializes a synthetic scenario repository under a caller-supplied temporary directory, drives the scripted in-memory provider surfaces, projects each boundary-returned domain event into the synthetic machine state (the governed-commit simulation the human operator performs in Stage 1, guarded after every write by the CTRL-001 authority checker), and records the durable evidence — it contains no transition table, no merge predicate, no review-selection rule, and no classification logic of its own, introduces no new lifecycle state, and never advances `automationStage`. The scenario exercises the full change loop (one `REQUEST_CHANGES` iteration: the same PR, the same worker session, the verbatim machine-readable packet findings, the new head, and the re-approval bound to that head), the single authorized merge attempt through the CTRL-008 predicate, and the hardest partial-operation restart: the merge mutation lands while the governed state write is lost, so the restarted process — carrying only durable identity references — asks CTRL-009, which classifies `EXTERNAL_COMPLETION_OBSERVED` and directs the merge boundary, whose external-merge continuation records the observed merge with **zero second `PUT`** (the per-step provider-call log is the proof surface: exactly one merge mutation, two worker starts — dispatch plus the fork-guard provenance re-proof — one resume, and read-only classification everywhere else). The typed `DogfoodExecutionRecord` carries every step's boundary, lifecycle positions, applied event, observed identity facts, and provider calls, plus the restart plan, the terminal `AWAITING_GOVERNANCE` classification, two fail-closed probes (a contradictory foreign session refused before any provider call, and the `PARTIAL_MUTATION_UNRESOLVED` partial mutation stopped without retry), and the explicit Stage-6 prerequisite statement — while preserving the automation stage verbatim. Two runs from equally built fixtures produce equal records, and the committed `tests/dogfood_execution_record.json` is replayed and compared on every test run (AC6). Everything is offline and deterministic (`tests/test_dogfood.py`); no network or tokens are needed.

### Production controller runtime (CTRL-011)

`controller/runtime.py` is the production Controller process over the accepted Stage-7 boundaries: the runnable one-shot (`cycle`) and bounded long-running (`run`) governed loop. `ControllerRuntime` composes exactly the accepted boundaries — it constructs the CTRL-005 orchestrator, CTRL-006 evidence gate, CTRL-007 review loop, CTRL-008 merge/reconciliation loop, and CTRL-009 recovery boundary over injected adapters — and **duplicates no predicate**: every cycle re-verifies repository authority first (fail-closed before any remote action), reconstructs the active position through CTRL-009, routes exactly the one boundary step the plan names (the boundary re-derives its own position and applies its own frozen predicate; a misrouted cycle fails closed through the boundary's typed position error), projects the boundary-validated domain event through the guarded `RuntimeRecorder` (machine-state `status` + work-order `Status:` line — exactly the two authority-checked surfaces, re-verified after every write; the reconciliation record projects the completed ledger and nothing else), and emits a structured `RuntimeCycleReport` (deterministic, serializable; provider mutations appear as method+path only). Non-authoritative execution references (branch, dispatch base, worker session, architect reviewer) are carried **in memory only** and rebuilt after restart from external process configuration plus live provider evidence — the request-form session is a reference, never proof, and the consuming boundary re-proves provenance (FZ-CTRL005-002). Provider tokens come only from the process environment (`CONTROLLER_GITHUB_TOKEN` / `CONTROLLER_ZAI_TOKEN`), never from repository files, and every output path is redaction-guarded. The long-running mode polls with multiplicative backoff capped at a configured maximum, sleeps only between unchanged-evidence observation cycles, resets the backoff after an advancing cycle, and is bounded by a hard per-invocation cycle cap; governance positions (awaiting-governance, partial-mutation-unresolved, evidence-ahead) end the loop cleanly — hold, never guess, never replay. The runtime performs no git operations and never merges, approves, completes, or advances: durable remote authority stays with the Architect. `controller/__main__.py` exposes the CLI (`validate`, `domain`, `status`, `cycle`, `run`) with structured operator output (`--json`) and fail-closed exit semantics (0 = completed, 1 = fail-closed, 2 = cycle cap reached). The CTRL-001 authority checker's mechanical-controller rule expectation is stage-derived (CTRL-011, explicitly flagged for Architect review): `humanOperatorIsTemporaryMechanicalController` is expected `false` at exactly the accepted Stage-7 marker and `true` at every other stage, matching the accepted Stage-7 transition's transfer of the routine mechanical-orchestration role to the Controller. The test suite (`tests/test_runtime.py`) exercises the runtime offline through the deterministic fakes — one-shot dispatch/begin-implementation cycles, boundary routing (evidence gate, review observation, governance-complete), bounded polling/backoff/cap semantics, restart reconstruction from external configuration with zero session database, recorder refusal classes, token isolation, CLI surface and fail-closed-before-network behavior.

### Error semantics

Every failure raises a typed `ControllerError`: `SpecError` / `ContradictionError` / `InvalidTransitionError` / `DomainError` family (authority, lifecycle, domain), the `GithubAdapterError` family (transport, auth, rate limit, not found, malformed, ambiguity, stale base, contradiction, merge blocked, forged authorization), the `ZaiAdapterError` family (configuration, auth, rate limit, transport, rejected request, malformed response, missing session, context mismatch, contradiction, policy violation), the `OrchestrationError` family (authority/remote contradiction, missing carried reference), the `EvidenceGateError` family (defective policy, out-of-position evaluation, authority/remote contradiction, missing carried reference), the `ReviewLoopError` family (out-of-position evaluation, authority/remote/evidence contradiction, missing carried reference, missing/ambiguous/malformed packet), the `MergeLoopError` family (defective policy, out-of-position evaluation, authority/merge-evidence contradiction, missing carried reference), and the `RecoveryLoopError` family (terminal exception position, authority/remote/evidence contradiction, missing carried reference). The CTRL-010 dogfood adds no new error family: its fixtures fail loudly through the existing typed taxonomy, and an internal scenario inconsistency raises the existing `ContradictionError` (never a silent pass). CTRL-011 adds exactly two runtime-process families, both fail-closed by construction: `RuntimeConfigurationError` (unusable externally supplied process configuration — missing external provider tokens, degenerate polling bounds, empty policy inputs) and `RuntimeRecorderError` (a governed recording that would leave authority invalid, cross-item, stale, or malformed — the write is refused and the runtime stops). All failures stop the operation; nothing is guessed, repaired silently, or retried implicitly.

## Operating the Controller (CTRL-011)

This section is the operator documentation the CTRL-011 work order requires: exactly how to install, configure, run, supervise, and stop the Controller for a real governed repository.

### Install

The Controller is pure Python standard library (Python >= 3.10) with zero runtime dependencies. Clone the controlled repository and run from its root — there is nothing to install, build, or migrate, and no controller database exists anywhere:

```sh
git clone https://github.com/pectoraux/controller.git
cd controller
python -m controller validate --repo .   # offline sanity check: authority must verify
```

### Configure

The runtime reads **only** process-environment configuration. The two provider tokens are mandatory for the governed commands (`cycle`, `run`) and are never read from repository files, never written anywhere, and never emitted in logs or reports (a redaction guard sits on every output path):

```sh
export CONTROLLER_GITHUB_TOKEN="ghp_…"     # the operator's GitHub token
export CONTROLLER_ZAI_TOKEN="zai_…"        # the provider (Z.ai) worker token
```

Every governed invocation also names, as explicit CLI flags, the fresh policy inputs the frozen boundaries require — the required CI check contexts, the retryable subset, and the Architect's GitHub identity whose reviews are decisions. The non-authoritative carried references (`--branch`, `--base-sha`, `--session-id`) are the identity references the operator reconstructed from the delivery transcript; after a restart, supplying `--session-id` with `--base-sha` lets the owning boundary re-prove the worker session's provenance from live provider state — the runtime never guesses a missing reference, and a genuinely absent one fails closed with the boundary's typed missing-reference error. The repository identity (`--repository`, default) and API roots default to production values and can be redirected for controlled environments.

### Run

One deterministic governed step — authority is re-verified first, exactly one boundary step executes, the validated event is projected through the guarded recorder, and one structured report is emitted:

```sh
python -m controller cycle --repo . \
  --required-checks "ci/tests,ci/validate" \
  --architect-reviewer pectoraux \
  --branch ctrl-011-production-controller-runtime \
  --base-sha 0c6727dc189fb0ae277416a676cf43a12062eeaa
```

The long-running mode repeats governed cycles with bounded polling (base interval, multiplicative backoff capped at a maximum, reset after every advancing cycle) and a hard per-invocation cycle cap; unchanged non-terminal evidence (CI pending, review pending) is observed and polled, never busy-looped:

```sh
python -m controller run --repo . \
  --required-checks "ci/tests,ci/validate" \
  --architect-reviewer pectoraux \
  --branch ctrl-011-production-controller-runtime \
  --base-sha 0c6727dc189fb0ae277416a676cf43a12062eeaa \
  --session-id zai-sess-ctrl-011-001 \
  --poll-interval 60 --poll-backoff 2.0 --poll-max 600 \
  --max-cycles 1000
```

Add `--json` for machine-readable operator output (one JSON object per cycle) suitable for log aggregation. Exit codes: `0` = completed, paused for governance, or lifecycle complete; `1` = fail-closed (a `FAIL-CLOSED:` line names the typed error on stderr); `2` = the cycle cap was reached without a terminal position (restart the process; every position is reconstructible).

### Supervise

The runtime is intentionally supervision-friendly: it is stateless across restarts (all durable truth is the repository plus GitHub evidence), it exits non-zero on every fail-closed condition instead of retrying, and it never daemons or spawns background threads of its own. Run it under the operator's service manager (systemd, Docker restart policy, Kubernetes job, or a shell loop) with `Restart=on-failure` and a restart delay; the bounded polling and cycle cap mean a crashed or killed process never leaves partial remote effects unobserved — the next start re-classifies the position through the CTRL-009 recovery boundary (an externally completed mutation is recorded, never re-attempted; a partial mutation with no observed outcome holds for governance attention). A recommended unit pattern:

```ini
[Service]
WorkingDirectory=/srv/controller
EnvironmentFile=/etc/controller/tokens.env   # CONTROLLER_GITHUB_TOKEN / CONTROLLER_ZAI_TOKEN
ExecStart=python3 -m controller run --repo . --required-checks ci/tests,ci/validate --architect-reviewer pectoraux --json
Restart=on-failure
RestartSec=30
```

Feed stdout/stderr to the operator's log pipeline; the structured JSON reports are the telemetry surface (authority fingerprint per cycle, recovery classification, boundary invoked, applied event, provider mutations as method+path, operator guidance). Reports are never authority — the repository stays the sole durable truth.

### Stop

Send `SIGTERM` (or the supervisor's stop command); the runtime has no background state to flush — the current cycle either completed or did not, and both are safe. Stopping mid-cycle cannot strand the loop: the governed positions are idempotent, the merge boundary performs at most one mutation attempt per authorized head, and any interruption is classified on the next start. To stop operating permanently, disable the supervisor unit — the repository, its authority, and the governance boundaries remain complete and usable offline (`validate`, `domain`, `status`).

### Safety boundaries while operating

The runtime never merges, approves, completes, or advances a Work Item on its own authority: the one authorized merge executes only inside the CTRL-008 boundary when its frozen predicate (exact head, terminal-success required CI, the Architect's exact-head approval) holds, and post-merge advancement stays with the Architect. Fail-closed conditions — malformed or contradictory authority, stale correlation, provider failures, ambiguous state — surface as typed errors with non-zero exits and are never retried implicitly; the operator (or the Architect, for governance holds) resolves them explicitly. The one-Work-Item/one-PR rule and the worker-merge prohibition are enforced by the frozen predicates the runtime composes, not by the runtime itself.
